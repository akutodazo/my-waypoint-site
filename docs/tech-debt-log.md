# 技術負債カルテ（症例集）

対象: field_share / my-waypoint-site
役割: **過去に発生した技術負債の症例記録**。症状→原因→修正→予防を1症例ずつ残す。
[tech-debt-guard.md]（予防ルール）と対になる文書で、カルテ=症例、ガード=蒸留された規則。
初版: 2026-07-19（技術負債調査 2026-07-18 とその解消実績から作成）

## 使い方

1. **仕様書・負債解消の依頼文に本書全体を添付する。** AIはコード全体の調査から
   始めるのではなく、まず既知症例との照合から始めること
2. **負債を修正したら、同じPRで本書に症例を追記する**（記入形式は下記）
3. **昇格ルール**: 同じ傾向の症例が2〜3回繰り返したら、ガードのチェック項目または
   CIの自動検査へ昇格させ、症例側に昇格先（例: ガード§3）を記す
4. 原本は `projects/docs/技術負債カルテ.md`。両リポジトリに `docs/tech-debt-log.md`
   として複製している。**改訂したら3箇所を同期すること**

## 傾向と対策（これまでの症例の4分類）

| 分類                | 典型症状                                                       | 対策                                             | 予防                                               |
| ------------------- | -------------------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------- |
| ①検査の穴型         | 重要処理・データ整合がテスト/CIの対象外で、壊れても緑のまま    | 「壊れたら何が起きる？」が怖い順にテスト化しCIへ | ガード§3（怖い処理へのテスト必須）                 |
| ②知識の重複型       | 同じ数字・事実が2箇所以上にあり、片方だけ更新されてずれる      | 名前を付けて集約ファイルへ一元化                 | ガード§3（定数集約）・§4（文書に固定数を書かない） |
| ③規約違反の見逃し型 | 自分で決めた掟（層の依存方向等）への違反が混入し、後続が真似る | 発見次第すぐ修正（放置すると雪だるま）           | ガード§3（層の掟）・レビュー観点化                 |
| ④環境・運用型       | コード外の要因（改行コード・ブランチ・置き場・バックアップ）   | 環境設定ファイル・置き場ルール・自動削除設定     | ガード§6・定期点検メニュー（ガード§9）             |

## 記入形式

```
### <ID> <一言タイトル> [分類] — 状態（対応済み/未対応/凍結）
- 症状: どう気づいたか
- 原因: なぜ生まれたか
- 修正: 何をしたか（日付・PR）
- 予防: 仕組み化したか・ガードへ昇格したか
```

## 症例集: field_share

### FS-1 データ整合をCIが検証していなかった [①検査の穴] — 対応済み

- 症状: fields.json / photo-manifest.json / public/photos の整合を守るのが「手順の記憶」だけ。photos:sync忘れでもCIが緑のままマージできた
- 原因: CIに lint/format/test/build しかなく、データの検査が無かった
- 修正: photos:check 新設（manifest整合・孤児圃場・公開写真のEXIF/XMP残存走査）、npm run check と CI に組込（2026-07-18）
- 予防: ガード§3へ昇格。**後日オルソ導入時に同パターンを ortho:check として横展開（PR#47）＝対策が再利用された成功例**

### FS-2 EXIF/XMP除去（GPS流出防止）が未テスト [①検査の穴] — 対応済み

- 症状: サイト最重要の安全装置が、sharp のライブラリ更新で黙って壊れうる状態
- 原因: スクリプト層（photos-import）にテスト文化が及んでいなかった
- 修正: importPhoto をコアへ分離しテスト3本（EXIF+XMP両方の除去・1600pxリサイズ・原本SHA-256前後一致）。**DJIはGPS・高度をEXIFでなくXMP(drone-dji:\*)にも書くため、EXIFだけの検証は不十分**（2026-07-18）
- 予防: ガード§3「怖い処理」該当例として明記。テスト用フィクスチャは偽座標の生成画像（実写真はそれ自体が流出源）

### FS-3 元写真（唯一のメタデータ源）がローカルのみ [④運用] — 対応済み

- 症状: photos_inbox/processed/ の XMP付き元写真48枚が gitignore 対象でPC故障と同時に消える状態。ジオリファレンス機能の唯一の入力源
- 原因: gitignore は「コミットしない」であって「保全しない」ではないことの見落とし
- 修正: 外部バックアップ実施（2026-07-18、手動）
- 予防: ガード§9定期点検。新たな「git外の一点物データ」が生まれたら即バックアップ対象に加える

### FS-4 テストが実データ（圃場48件）に密結合 [②重複] — 未対応

- 症状: static-field-repository.test.ts が「48件・393〜440」を前提にしており、圃場を1件足すとアプリは正常なのにテストが落ちる
- 原因: テストを「その時のデータのスナップショット」として書いた
- 修正: 未対応。対処案=件数の一致ではなく性質（正の件数・id昇順・必須フィールドの存在）を検証する形へ書き換え
- 予防: 放置すると「テストが落ちても数字を書き換えるだけ」の習慣化→テストへの信頼が死ぬ。次に圃場を追加するPRで同時に直すのが効率的

### FS-5 DESIGN.md の構成図が実装と乖離 [④運用] — 対応済み

- 症状: 存在しないファイル名（photo-gallery.tsx）や旧拡張子（.mjs）が記載され、それを信じたAI/未来の自分が間違った前提で作業する危険
- 原因: 実装中の設計変更時に文書を更新しなかった
- 修正: docs/fix-drift（PR#48）で乖離を解消
- 予防: ガード§4「文書はコードと同じコミットで更新」へ昇格

### FS-6 設計文書が未コミットでローカルのみ [④運用] — 対応済み

- 症状: photo-overlay-palette.md（設計判断の記録を含む）が git 管理外で消失リスク。置き場方針（docs/ か ai-handoff/ か）も未決だった
- 原因: 「恒久設計文書」と「AIへの作業メモ」の置き場ルールが無かった
- 修正: docs/ へコミット（2026-07-19）
- 予防: 置き場ルール=恒久設計は docs/（コミット）、作業パケットは ai-handoff/（gitignore）

### FS-7 単写真ジオリファレンス（PR32）の保留 [参考: 管理された凍結] — 凍結

- 症状: ヨーの系統誤差と品質判定が未解決で機能を保留・クローズ
- 原因: （負債ではなく技術的難所。カルテには「凍結の正しい残し方」の手本として記録）
- 修正: ブランチ feature/georef-projection / feature/georef-spike に温存し、知見を docs/georef-spike-findings.md に文書化、CLAUDE.md にも保留と明記
- 予防: 未完成機能を消すのでも main に混ぜるのでもなく「ブランチ温存+知見の文書化+status明記」の3点セットで凍結する

## 症例集: my-waypoint-site

### WP-1 中核Presenterが未テスト [①検査の穴] — 対応済み

- 症状: Service層は全てテスト済みなのに、それらを束ねる use-waypoint-planner（モード分岐・200点上限警告）だけ検査網の外
- 原因: 「ロジックはServiceに」の意識が強く、オーケストレーション層の検査が抜けた
- 修正: renderHookテスト11本追加。後付けのため「わざと壊して赤を確認→復元」で検査能力を証明（2026-07-18）
- 予防: ガード§2（後付けテストの証明手順）へ昇格

### WP-2 度→m換算111320の重複とドメイン定数の散在 [②重複] — 対応済み

- 症状: 111320 が route-generator と overview-shots に別々に存在。DJI上限200点・高度上限149m・カメラ諸元も3ファイルに散在し、機体変更時の修正点が閉じない
- 原因: 新ファイル作成時に既存定数を探さず再定義した
- 修正: services/flight-constants.ts に集約（2026-07-18）
- 予防: ガード§2（既存資産の調査）・§3（定数集約）へ昇格。報告形式に「既存資産の調査結果」欄を新設

### WP-3 UI層がフック/Serviceを直import [③規約違反] — 対応済み

- 症状: search-box が usePlaceSearch を、preset-bar が FLIGHT_PRESETS を直接import。ARCHITECTURE.md「UIはpropsで受け取るだけ」に違反
- 原因: 実装時の近道。掟はあったが検査する仕組みが無かった
- 修正: page側で配線しpropsで渡す形へ（PlaceSearch型を types/domain に新設、2026-07-18）
- 予防: ガード§3へ昇格。違反を1つ放置すると後続コードが真似るため発見次第修正

### WP-4 READMEの固定数「38 tests」が陳腐化 [②重複/④運用] — 対応済み

- 症状: テストは61本に増えていたのに文書は38のまま＝文書が嘘をつく状態
- 原因: 増減する値を文書に固定値で書いた
- 修正: 固定数の記載自体を削除（2026-07-18）。歴史的な進捗ログの「計38本」は当時の記録なので残す
- 予防: ガード§4「陳腐化する固定値を書かない」へ昇格

### WP-5 CRLF問題が未対策（field_shareの教訓が未展開） [④環境] — 対応済み

- 症状: autocrlf=true 環境で checkout し直すと作業ツリーがCRLF化し、触っていないファイルまで Prettier のローカル検査が落ちる
- 原因: field_share で解決済みの教訓（.gitattributes）が他リポジトリへ展開されていなかった
- 修正: `* text=auto eol=lf` の .gitattributes 追加+作業ツリー正規化（2026-07-18）
- 予防: **1つのリポジトリで得た環境系の教訓は、他の全リポジトリと新規立ち上げテンプレートに即展開する**

### WP-6 マージ済みブランチの放置 [④運用] — 対応済み

- 症状: 規約「マージ後は即削除」に反しリモートに4本残存
- 原因: 手動削除は忘れる
- 修正: 削除（2026-07-18〜19、field_share側の残存2本も含む）
- 予防: GitHubリポジトリ設定「Automatically delete head branches」をONにすれば作業自体が消える（要ユーザー操作・両リポジトリ未設定なら推奨）
